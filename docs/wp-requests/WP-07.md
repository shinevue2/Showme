## R1 · WP-00 / WP-11: the stage does not follow sticky placeholders
`src/gl/stage/index.ts` caches each placeholder's document position (`docTop`) and draws at `docTop − scrollY`.
A placeholder inside a `position: sticky` stage keeps its *viewport* position while stuck, so after one screen of
scrolling the stage would draw the view off screen and then drop it from the live set (its cached area is 0).
- Workaround in `works/index.ts`: on every scroll update of the works section (ScrollTrigger / Lenis `scroll`, which
  fires before the frame) it calls the stage's public `measure()`. Cheap (one rect read per view, layout is clean),
  but it re-measures every view.
- Proper fix (stage): for records whose placeholder has a sticky ancestor, take the rect from the
  IntersectionObserver entry / one `getBoundingClientRect()` per frame while `seen`, or re-measure sticky records in
  the scroll handler. `cover-block` (WP-05, sticky cover stage) needs the same.

### R10 · WP-00 / WP-11 (stage): compile the post-RT program variant during warm-up
`warm()` runs `renderer.compileAsync(scene, camera)` with the canvas bound, but on the high tier views draw into
the post pass's half-float RT, whose output colour space is linear: three links a second program variant
(`srgb-linear`) lazily at the first visible frame, i.e. a compile stall on screen (DESIGN §10.1 "no compile
stall > 50 ms while a view is visible"). `works-byobu` works around it in `prewarm()` (compiles once with a 1×1
half-float RT bound). Proper fix in `src/gl/stage/index.ts` `warm()`: when `tier.post`, also compile with
`post.rt` bound — every view (cover, skills, garden, …) has the same second variant. Program counts per view are
therefore 2 on the high tier (one per target), stable across tier changes.
